# 安全模型与当前边界

> ⚠️ **先读这句**：本文如实区分「**已实现**」与「**尚未实现**」。
> 目标定位包含**按权限调用**与**可审计**，但这两项**当前尚无代码实现** ——
> 具体见 [能力矩阵](./README.md#能力矩阵) 与下文「权限与审计」一节。

## 一、凭证模型（已实现）

**核心原则：凭证不进 prompt、不进文档、不落盘。**

目标 API 的凭证通过**环境变量**注入，由 `AuthManager` 在转发时附加到请求头：

```
SOURCE → 环境变量 → AuthManager.getHeaders(source) → Authorization: Bearer <token>
```

- 凭证只存在于**进程环境**中，不出现在 tool 描述里，Agent 与 LLM **看不到明文凭证**
- LLM 侧凭证（`ANTHROPIC_API_KEY` / `OPENAI_API_KEY`）与目标 API 凭证**各自独立**

### 自动识别（`autoDetectAuth`）

启动时按 source 名匹配一组**硬编码的服务名**，命中且对应环境变量存在时注册 bearer 认证：

| source 关键字 | 环境变量 |
|---|---|
| `github` | `GITHUB_TOKEN` |
| `notion` | `NOTION_API_KEY` |
| `feishu` | `FEISHU_APP_TOKEN` |
| `wechat` | `WECHAT_TOKEN` |
| `slack` | `SLACK_TOKEN` |
| `openai` | `OPENAI_API_KEY` |
| `anthropic` | `ANTHROPIC_API_KEY` |

### 边界（务必知悉）

| 事实 | 影响 |
|---|---|
| **仅支持 bearer** | 需要 API Key 头、Basic、OAuth 等服务需自行调用 `AuthManager.register()` 扩展 |
| **只自动识别上表 7 个服务** | 其他 source **不会自动注入凭证**；转发将在**无凭证**状态下发出 |
| **未命中时无提示** | 上述「无凭证转发」不会打印任何警告 |

## 二、权限与审计（❌ 尚未实现）

> 这一节描述的是**当前状态**，不是目标状态。

| 能力 | 现状 |
|---|---|
| **按权限调用** | 未实现。代码中无权限 / 策略 / 角色模型。**任何能访问端点的调用方，对所有已注册的 tool 等价可用** |
| **审计日志** | 未实现。无调用留痕、无 trace、无可追溯记录 |
| **参数校验 / 白名单** | 未实现。调用方入参经拼接后直接转发 |
| **工具级可见性控制** | 未实现。`tools/list` 返回全部已注册 tool |

因此，**当前版本不应被当作"已具备访问控制"的网关使用**。

## 三、部署注意（当前版本）

1. **默认绑定 `127.0.0.1`** —— 仅本机可访问，这是默认且推荐的形态
2. **`--host` 可改为对外监听，但端点自身没有鉴权** —— 改为 `0.0.0.0` 等于把
   「所有已注册 tool」暴露给网络；在补齐鉴权前，**不要把服务直接暴露到网络**
3. **反向代理** —— 若确需对外，应在前面加一层带鉴权 / 限流 / IP 白名单的代理
4. **最小权限令牌** —— 注入的目标 API 令牌应尽量只授予必要范围（如只读 scope）

## 四、输入面（当前版本）

转发层会做以下处理，**均不含安全过滤**：

- 路径占位符（`{param}`）由调用方参数替换进 URL
- 其余参数：`GET` 追加到 query string，非 `GET` 整体作为 JSON 请求体
- **无类型校验、无长度限制、无字符转义、无目标地址校验**

> 结论：**在补齐「参数校验 + 权限模型 + 审计」之前，本项目的定位是"能跑通链路"，而不是"可安全托付的生产网关"。**
